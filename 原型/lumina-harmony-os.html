01 · Strategic Positioning

§1 战略定位

1.1 · 背景

近年来高校信息化采购中信创（信息技术应用创新）诉求持续上升，国产操作系统与终端设备进入合规目录成为诸多高校的招标硬性条件。与此同时，HarmonyOS NEXT（纯血鸿蒙）生态自 2024 年快速崛起，华为 / 荣耀新机型装机量高速增长，高校师生群体中的鸿蒙设备持有比例已成规模。

但Expo 官方不支持鸿蒙——Lumina 现有移动端（React Native / Expo SDK 52）无法直接输出鸿蒙版本，鸿蒙端是当前跨端矩阵中的空白。

1.2 · Lumina 跨端矩阵现状

端技术栈状态说明
iOS / AndroidReact Native / Expo SDK 52✅ 已实现服务/mobile-app/，功能对齐 Web
WebReact 18 + TS + Vite✅ 已实现服务/web-frontend/
桌面Electron（规划中）🟡 原型原型/PC/，TDD §3.2
鸿蒙 HarmonyOS—⏳ 空白（本文档补齐）Expo 不支持，需独立技术路线（见 §6）

1.3 · 定位与价值

🎯 定位
鸿蒙作为第五端纳入 Lumina 跨端矩阵，与 iOS / Android / Web / 桌面并列；复用现有后端 API（同接口契约，见 §7/§8），客户端以 ArkTS + ArkUI 原生开发为主路线。
  • 目标用户：高校师生中的鸿蒙设备用户（华为 / 荣耀新机型，HarmonyOS NEXT 5.0+）
  • 商业价值：进入信创市场 · 满足高校采购合规要求 · 以「分布式跨端体验」形成差异化竞争
  • 节奏约束：对齐 WBS-P D-11「演进评估，不阻塞 M4」，作为 M4 之后的平台扩展批次
👨‍🏫
周老师 · 某高校教务处信息化负责人
Driver Persona · 信创采购
"今年智慧教室招标要求终端与操作系统进入信创目录，教室里的 MatePad 和智慧屏都跑鸿蒙——教学平台如果没有鸿蒙客户端，采购评分直接扣分。"

鸿蒙生态覆盖 6 类设备形态，Lumina 按教学场景价值 × 装机规模 × 适配成本排出优先级：

设备形态屏幕尺寸使用场景优先级

2.1 · 各形态适配要点

📱 鸿蒙手机 P0
  • UI：单列纵向布局，对齐 mobile-app 6 页面信息架构
  • 交互：触控 + 手势返回，答题选项大按钮（≥44vp）
  • 性能：中低端芯片保帧，直播走 HLS 自适应码率
📲 鸿蒙平板 P0
  • UI：双栏（列表 + 详情），直播/笔记分屏并显
  • 交互：支持 M-Pencil 手写批注、键盘快捷操作
  • 性能：高分屏渲染，视频硬解 + 后台小窗播放
💻 鸿蒙 PC P1
  • UI：三栏布局，向 Web 端信息密度看齐（批阅工作台）
  • 交互：鼠标/快捷键优先，多窗口并行（直播 + 名单）
  • 性能：批量导入/导出大表格虚拟滚动
📺 智慧屏 P2
  • UI：演示模式（大字距、去导航），仅投屏 + 答题统计视图
  • 交互：遥控器方向键 / 手机端遥控，无触控假设
  • 性能：1080P/4K 拉流稳定，长时间开机内存回收
⌚ 穿戴设备 P3
  • UI：卡片式极简：今日课表 / 待办作业 / 签到按钮
  • 交互：抬腕即看 + 一键签到，消息快捷回复
  • 性能：轻应用（Atomic Service）形态，低电耗轮询
🚗 车机 P3
  • UI：音频课程模式，行中禁止视频/答题交互
  • 交互：语音播报 + 大控件，接入鸿蒙座舱音频焦点
  • 性能：弱网断点续播，后台音频常驻
📘 一次开发 · 多端部署
手机 / 平板 / PC 三形态依托 ArkUI 断点响应式布局（sm/md/lg）共用一套代码交付；智慧屏 / 穿戴 / 车机为独立轻量形态，Phase 3 起逐项评估，不摊入 P0 成本。

03 · OS Support

§3 操作系统支持（三大鸿蒙形态）
🚀
1 · HarmonyOS NEXT（华为商用 · 2024+）主目标
  • 纯鸿蒙内核，不兼容 Android APK，必须原生 ArkTS/ArkUI 应用
  • 应用开发：ArkTS + ArkUI（DevEco Studio）
  • Lumina 鸿蒙版的主要目标平台，新版本设备与上架渠道均以此为准
🎓
2 · OpenHarmony（开源版本 · 教育 / 政企定制）
  • 开放原子基金会开源项目，支持定制发行版（如校园信创教育定制版）
  • 目标：高校信创专属设备（定制智慧教室终端、校园平板）
  • Lumina 侧承诺：通过 OpenHarmony 兼容性认证（见 §9 AC-12），纳入信创目录适配证明
🌉
3 · HarmonyOS 4.x 及更早（兼容期 · 2024 前设备）
  • 兼容 Android APK（方舟编译器），现有 mobile-app（Expo RN）构建产物可直接安装
  • 过渡期方案：存量用户先用 Android 版顶替，不发鸿蒙原生功能
  • 长期策略：引导逐步迁移到 NEXT 原生客户端，Android 兼容通道维护至 2027 后评估下线

04 · Distributed Features

§4 分布式能力（鸿蒙独有卖点）

分布式软总线是鸿蒙区别于 iOS/Android 的结构性差异，也是 Lumina 打入智慧教室场景的核心抓手。落地场景如下：

分布式能力Lumina 应用场景
🔄 跨设备流转 手机上看到一半的直播 → 流转到平板继续；课堂答题 → 一键流转到智慧屏展示统计结果
👥 多端协同 教师 PC 开播 → 学生平板 / 手机 / 教室智慧屏多端同步观看，课堂状态（举手/答题）跨端一致
🗂️ 分布式数据 学习进度 / 笔记 / 播放记录在多设备间实时同步（分布式数据对象，见 §7）
📡 软总线 教室场景：教师设备自动发现同课堂学生设备 · 一键投屏 · 无网也能近场互联
🃏 原子化服务 课程通知 / 作业提醒 / 今日课表以服务卡片形式直达桌面，无需打开 App 即可触达
⚠ 交付边界
分布式能力依赖同华为账号 + 同局域网/近场条件，且智慧屏 / 穿戴设备需独立轻量端配合。Phase 1-2（§5）不承诺上述体验，统一归入 Phase 3 差异化批次，避免核心教学链路被拖慢。

06 · Migration Strategy

§6 与现有移动端的迁移策略（三条路线）

WBS-P 已就鸿蒙路线做过预评估（Expo 官方不支持鸿蒙），本节固化三条路线的对比结论。

🅰️
路线 A · 原生 ArkTS / ArkUI 独立客户端推荐
  • 优势：性能最优 · 完整鸿蒙特性（分布式 / 原子化服务均可用）· 可上华为应用市场
  • 劣势：独立代码库 · 长期双端（RN + ArkTS）维护成本
  • 适用判断：Lumina 移动端仅 6 页面，信息架构简单，独立开发可控
🅱️
路线 B · RNOH（React Native OpenHarmony）
  • 优势：复用现有 React Native 代码 · 团队熟悉
  • 劣势：需从 Expo managed 迁移到 bare workflow（改动大）· RN 三方依赖需逐个替换鸿蒙适配版 · 生态不成熟
  • 适用判断：大型 RN 项目渐进迁移场景，对 6 页面体量性价比低
🅲
路线 C · uni-app 跨端
  • 优势：一套代码编译到多端（iOS / Android / 鸿蒙 / H5 / 小程序）
  • 劣势：性能损耗 · 鸿蒙特性（分布式、原子化服务）受限 · 现有 RN 资产全部作废重写为 Vue
  • 适用判断：快速铺开、不追求极致体验的新项目，不适配 Lumina 现状

6.1 · 路线对比矩阵

维度路线 A 原生 ArkTS路线 B RNOH路线 C uni-app
代码复用率低（仅复用 API 契约）高（复用 RN 组件逻辑）无（需重写为 Vue）
运行时性能⭐⭐⭐⭐⭐ 原生⭐⭐⭐ 桥接损耗⭐⭐⭐ Web 渲染损耗
鸿蒙特性支持完整（分布式 / 卡片 / 流转）部分（原生模块可桥接）受限
维护成本中（新增一套代码库，页面少）中（依赖升级双重跟踪）中（全家桶绑定）
生态成熟度高（官方主推）低（社区早期）中（鸿蒙编译持续完善）
结论✅ 采用落选落选
🎯 决策结论
采用路线 A：ArkTS / ArkUI 原生独立客户端（工程目录规划为 服务/harmony-app/，落地时随开发工作流创建）。同时保留 HarmonyOS 4.x 用户经 Android 兼容通道过渡（§3-3），两条腿走路。

07 · Data Model

§7 数据模型（后端零新增表）
🗄️ 后端
不新增任何后端表——鸿蒙版完全复用现有 API 与数据库（与 iOS / Android 同接口契约），服务端对客户端形态无感知（除设备注册信息外）。

7.1 · 客户端本地存储

存储机制鸿蒙 API承载数据生命周期
Preferences（轻量配置） @ohos.data.preferences 用户偏好 / 主题 / 通知开关 / 登录态缓存 持久，卸载清除
关系型数据库 @ohos.data.relationalStore 离线课程缓存 / 本地笔记草稿 / 直播播放记录 / 待同步操作队列 持久，LRU 清理（上限 500MB）
分布式数据对象 @ohos.data.distributedDataObject 跨设备同步的会话状态（当前播放位置 / 草稿 / 阅读进度） 会话级，冲突以服务端时间戳仲裁
⚠ 一致性原则
客户端本地存储仅作缓存与体验加速，不作为事实源；服务端为唯一权威（single source of truth），离线写入需在恢复联网后按时间戳回放同步，冲突展示服务端版本并保留本地副本供用户确认。

08 · API Preview

§8 接口设计（复用 141 paths / 180 ops · 新增 2 端点）

鸿蒙客户端复用现有全部 API（141 paths / 180 ops · 14 模块，与 lumina-api.html v1.7 快照一致），认证、分页、错误结构、SSE 流式均与 Web / RN 端同契约，不产生分叉。

8.1 · 新增鸿蒙专属端点（可选，随 Phase 3 落地）

POST/devices/register
设备注册：上报推送 Push Token · 设备类型（phone/tablet/pc/tv/watch）· OS 版本 · 机型，用于分端推送与信创设备统计
POST/devices/harmony/card-refresh
原子化服务卡片数据刷新：为桌面卡片拉取今日课表 / 待交作业 / 打卡状态的聚合快照（轻量只读）
🔒 契约约束
新增 2 端点归属 user 模块（设备子资源），不新增业务模块；请求 / 响应 Schema 落地时需同步 OpenAPI YAML 与 API 文档（届时走开发 + 变更工作流联动）。
