01 · Background

§1 背景与目标

1.1 · 业务背景

Lumina 墨光已完成 M1-M4 主体功能（17 模块 · 单体 FastAPI），生产环境以 Docker Compose 编排 MySQL / lumina-app / Nginx 三服务运行。当前运维手段停留在「容器日志人肉翻阅 + 部署脚本 check.sh 契约核对」层面，缺少系统化的可观测性能力：

  • 无统一指标采集与趋势查询 —— 服务劣化（延迟爬升、错误率波动）无法提前感知；
  • 健康检查仅覆盖存活探针（/health / /health/ready）—— 依赖服务（DB / 缓存）故障无法定位到点；
  • 无告警触达链路 —— 故障依赖用户反馈才知道；
  • 业务视角数据（DAU / 提交量 / 考试量 / AI 调用量）散落各表，管理员无汇总入口。

D-10 任务包定义平台的「监控大盘 + 指标导出 + 深度健康检查 + 告警生命周期 + 采集降级」五项能力。应用侧（ops 模块 3 端点）已落地；采集/告警基础设施（Prometheus / AlertManager / Grafana）与告警处理闭环为本需求规划范围。

1.2 · 核心目标

目标维度描述量化指标
📊 指标可查询 系统指标（QPS / 延迟 / 错误率 / 资源）与业务指标统一导出，Prometheus 可抓取 指标采集间隔 ≤15s · 大盘刷新 ≤30s
🩺 故障可定位 深度健康检查逐依赖服务报告状态与延迟 故障定位时间（MTTL）≤ 5 分钟
🔔 告警可触达 阈值触发 → 通知 → 处理 → 复盘全生命周期闭环 P0 告警触达 ≤ 2 分钟 · 告警响应率 100%
🛡️ 采集不拖垮业务 指标采集异常时按降级策略保护主链路 采集自身开销 < 2% RT · 数据丢失率 < 0.1%
📘 定位
纯运维侧能力，不改变任何业务语义：ops 模块只读聚合既有数据（api_logs / ai_call_logs / 业务表计数），不新增业务写路径；告警处理复用 notif 模块既有通道（邮件 / 站内信，短信与企业微信为预留通道）。

02 · Features

§2 功能需求
🩺
A · 健康检查（已实现）

三级探针体系：GET /health（存活 liveness）、GET /health/ready（就绪 readiness）、GET /ops/health/deep（深度依赖检查）。深度检查逐项报告 MySQL / Redis / lumina-app 的 status（healthy / degraded / down）、latency_ms 与明细，并给出总体状态与 uptime_seconds。Redis 当前为 degraded（未部署，走内存缓存），部署后转为实际探活。

📈
B · Prometheus 指标导出（已实现 + 待扩展）

GET /ops/metrics 输出 Prometheus 文本格式（text/plain; version=0.0.4），当前含 7 项指标：lumina_users_total / lumina_courses_total / lumina_videos_total / lumina_api_requests_total{status} / lumina_active_users_today / lumina_ai_calls_total / lumina_uptime_seconds。

规划扩展（配合 Prometheus 抓取）：HTTP 请求时延直方图（P50/P95/P99）、进程 CPU / 内存占用、DB 连接池水位。由 Prometheus 以 15s 间隔抓取，Grafana 渲染监控大盘。

🧮
C · 业务指标汇总（已实现）

GET /ops/metrics/business（仅 admin 角色）返回 13 项业务快照：用户总量 / 今日活跃、课程总量 / 30 天活跃、视频总量 / 今日播放、作业提交、考试作答、AI 调用、打卡次数。作为管理后台「监控大盘」页面的数据源。

🔔
D · 告警生命周期（需求定义）

Prometheus Rule → AlertManager 分级路由：Warning（邮件摘要）/ Critical（即时触达：邮件 + 企业微信/短信预留）→ 管理员介入转 Resolving → 解决回 Normal；Critical 超时未处理自动升级（Escalated，通知上一级负责人）。每次告警的触发、认领、处理、复盘经 notif 模块与审计日志（logs 模块）留痕。阈值见 §4.2 状态机注记。

🛡️
E · 采集降级与自愈（需求定义）

指标采集失败或延迟过高时按五级策略降级：本地缓存批量上报 → 采样率动态调整 → 非关键指标异步化 → 关键指标同步保障 → 失败落本地日志补报。网络/服务恢复后自动补报并对账。详见 §4.4 异常流程。

03 · Acceptance

§3 用户故事与验收标准
编号用户故事验收标准（AC）优先级
US-1 管理员 我希望在监控大盘查看 QPS / 延迟 / 错误率 / 资源使用，以便随时掌握系统健康度 AC1: 大盘数据刷新延迟 ≤ 30s；AC2: 任一指标异常可从大盘下钻到详细日志（api_logs） P1
US-2 管理员 我希望依赖服务故障时收到分级告警并被闭环跟踪，以便及时介入 AC3: Critical 告警 2 分钟内触达；AC4: 告警按 §4.2 状态机流转，处理过程有记录与复盘 P0
US-3 管理员 我希望通过深度健康检查快速定位故障点（DB / 缓存 / 应用） AC5: /ops/health/deep 逐服务返回 status/latency/details；AC6: 总体状态聚合规则正确（down > degraded > healthy） P0
US-4 管理员 我希望查看业务指标（DAU / 提交 / 考试 / AI 调用）以支撑运营决策 AC7: /ops/metrics/business 13 项字段完整；非 admin 访问返回 403 P1
US-5 管理员 指标采集故障时不得影响教学主链路 AC8: 降级策略按 §4.4 五级生效；AC9: 采集成功率 ≥ 99.9% · 上报延迟 P95 < 1s · 数据丢失率 < 0.1%；AC10: 每小时数据对账（采集量 vs 上报量）差异可报告 P0
US-6 管理员 合规：监控数据涉及用户标识（user_id）与访问行为，须遵循最小必要与留存期限 AC11: 指标与大盘仅呈现聚合值，不展示个人可识别信息；api_logs 中 user_id 仅用于聚合统计；⚖️ 监控数据留存 ≥ 30 天供审计、到期归档（《个人信息保护法》最小必要 + 《数据安全法》数据分级） P0
⚖️ 合规预检结论（步骤 1.5）
命中合规域：个人信息处理（访问日志含 user_id / IP，需最小必要与目的限制 → AC11）；数据分级（监控数据属「一般」级，审计日志属「重要」级）。
未命中：未成年人新增采集（不新增采集学生身份数据，复用既有日志）· AI 生成内容 · 算法推荐 · 数据跨境（全部本地部署）· 电子签名。

04 · Business Flows

§4 业务流程定义

本节以 4 类视图固化 D-10 的核心业务语义：用户旅程（管理员查看监控大盘）、状态机（告警生命周期）、跨模块时序（健康检查与自动恢复）、异常流程（业务指标采集降级）。后续基础设施部署与测试（§8 RTM）均以本节流程为对齐基准。

    participant API as lumina-app API
    participant MySQL as MySQL
    participant Redis as Redis
    participant AlertManager as AlertManager

    Prometheus->>API: GET /health (每 15s)
    API->>MySQL: 检查数据库连接
    API->>Redis: 检查缓存连接
    API-->>Prometheus: {status: "healthy", checks: {...}}

    alt 健康检查失败
        Prometheus->>AlertManager: 触发告警
        AlertManager->>AlertManager: 评估告警规则

降级策略明细

#策略说明
1本地缓存 → 批量上报最多缓存 5 分钟数据，恢复后按序批量补报
2采样率动态调整高负载时采样率 100% → 10%，优先保住趋势可用性
3非关键指标延迟上报用户行为类指标进入异步队列，削峰填谷
4关键指标优先保障支付 / 登录类指标保持同步上报，不降级
5失败落本地日志采集失败写入本地日志文件，作为补报与审计兜底

监控指标（降级机制自身的 SLO）

指标目标
采集成功率≥ 99.9%
上报延迟P95 < 1s
数据丢失率< 0.1%

自动恢复

  • 网络恢复后自动补报缓存数据；
  • 服务重启后从检查点（checkpoint）继续；
  • 数据对账：每小时核对采集量 vs 上报量，差异超阈值触发 Warning 告警（回流 §4.2 状态机）。

05 · API Contract

§5 接口契约（ops 模块）

模块前缀 /ops，共 3 端点，均为只读。应用侧已实现；Prometheus 抓取 /ops/metrics 无需鉴权（仅内网暴露），/health* 供探针使用无需鉴权。

GET/ops/health/deep
深度健康检查 · 返回总体 status + 逐服务（mysql/redis/lumina-app）status/latency_ms/details + uptime_seconds（免鉴权）
GET/ops/metrics
Prometheus 文本格式指标导出（7 项，规划扩展时延直方图与资源指标）· media_type: text/plain; version=0.0.4（内网免鉴权）
GET/ops/metrics/business
业务指标汇总 13 字段（用户/课程/视频/作业/考试/AI/打卡）· 仅 admin 角色，越权 403

07 · Compliance

§7 合规与数据保护
合规域约束落地措施
《个人信息保护法》 最小必要 · 目的限制 监控面仅呈现聚合指标，大盘/报表不下钻到个体学生画像；/ops/metrics/business 仅 admin 可见
《数据安全法》 数据分级 系统指标 = 一般级；含 user_id/IP 的访问日志 = 重要级，留存 ≥30 天后脱敏归档
网络安全 端点暴露面控制 /ops/metrics 与 /ops/health/deep 经 Nginx ACL 限内网；生产环境 Prometheus 不与公网直通
